# 本番サーバーの同期バトル

## 利用する画面

| 用途 | パス |
| --- | --- |
| 運営PC・会場スクリーン | `/raid/screen`（管理者ログインが必要） |
| アプリ内の参加入口 | `/battle`（ホームと共通のQR読み取り） |
| 参加者のスマホ | `/battle/raid` |
| 演出だけの確認 | `/raid/screen?demo=effects` |
| スマホの独立した操作プレビュー | `/battle/raid?preview=1` |

現在の公開先では、スクリーンは `https://163.43.128.139/raid/screen`、参加者は `https://163.43.128.139/battle/raid` を開きます。参加QRは `APP_URL` のオリジンから作り、開発用LANアドレスは使いません。`APP_URL` は実際の公開HTTPS URLと一致させてください。Dockerではホストの `.env` だけでなく、webコンテナーへ渡す `compose.override.yaml` の環境変数を確認します。

`ENABLE_DEV_SIMULATOR=false` のまま動きます。本番で開発用モードを有効にする必要はありません。`?sync=local` と `/api/local-raid` は従来通り本番では利用できません。

CPU対戦は廃止しました。アプリの「バトル」では会場QRを読み取り、`/battle/raid` の同期バトルへ進みます。未登録の場合はゲスト登録後にQR参加画面へ戻ります。ホームにも同じ読み取りを残しています。QRは同一サイトの参加URLを確認する入口で、参加権限は既存のゲストセッションで検証します。読み取り前の `/battle` では部屋への参加処理を行いません。スマホの標準カメラから会場QRを直接開く導線も利用できます。

## 運営の流れ

1. 運営PCで `/raid/screen` を開き、管理者としてログインします。ログイン後はスクリーンに戻ります。管理画面ヘッダーの「会場スクリーン」からも開けます。
2. 待機中のスクリーンに表示される参加QRをスマホの標準カメラで読み取ります。初めての参加者はゲストではじめると、その部屋の受付へ戻ります。パートナーを選んで「このレイドに参加」を押して確定します。ページを開いただけでは参加人数に加算しません。
3. 参加キャラはNFC等で所持しているキャラから選びます。未所持の場合は、正式な通常キャラを使った体験参加ができます。体験参加でキャラ所持は増えません。
4. 参加者を確認し、画面下の操作バーにある「10秒の入力受付を開始」を押します。参加者0人では無効です。受付中・演出中はボタンが現在の進行状態を表示します。以後は10秒の入力→全員共通のじゃんけん→攻撃・自己回復→ボスの全体反撃→次の受付と進みます。
5. 討伐成功・全滅後は操作バーの「次のバトルを準備」で次のグループへ切り替えます。途中でリセットする場合は「同期設定」→「同期をリセット」を使います。リセットすると部屋IDとレイド用QRが変わり、前のスマホは自動再参加しません。次戦には新しいQRから参加確定が必要です。個人の完了記録・ポイント・実績は保持します。

操作バーは16:9の演出領域から分けて常時表示します。参加者名・キャラ名・HP・参加URLなどの文字は12px以上、操作ボタンは14px以上（開始・次のバトルは16px）を確保し、ブラウザの拡大や画面幅で文字を非表示にしません。参加者が多い場合は一覧内をスクロールできます。

運営PCはスクリーンを前面で表示し続けてください。スマホの勝敗・HPと次ラウンドの開始はスクリーンの演出通知に合わせます。タブを閉じたり非表示にした場合は進行が待機します。開き直すと保存済みの段階から再開します。複数の運営PCで同じバトルの演出を同時進行させないでください。管理者セッションは8時間です。操作中にログインを求められた場合は「同期設定」の管理者ログインから入り直します。

## 保存と権限

- イベントごとに1部屋、最大20人です。ボスのHPと全体攻撃は参加人数で調整します。10人ではHP4,500・全体攻撃14、20人ではHP9,000・全体攻撃17です。味方の基本攻撃50・基本自己回復30とじゃんけん倍率は維持します。[参加人数・旧データを含む強さのルール](raid-balance.md)を参照してください。完了した討伐成功は1人100ポイント、条件に応じた称号・バッジを付与します。[報酬の保存と既存記録への付与](player-awards.md)を参照してください。育成値の付与は未実装です。
- `RaidRoom` に参加者・入力・HP・結果・演出の公開段階・送信IDを保存します。再読み込み・webコンテナーの再起動後にも継続します。参加者の所持・NFCタグ・取得日時は変更しません。
- 戦闘完了時は個人別の勝敗を `RaidResult` に保存し、プロフィールの「冒険の記録」へ反映します。部屋のリセット後も残り、同じ部屋の結果は重複しません。収集状況と更新方法は [冒険の記録](adventure-records.md) を参照してください。
- `/api/raid` で同期します。参加・行動送信は有効なゲストセッション、開始・リセット・演出進行・スクリーン用取得は有効な管理者セッションが必要です。参加者からHP・攻撃量は指定できません。
- イベントの共有ロック→部屋の更新ロックの順で処理し、複数のプロセスからも同じ部屋を更新します。1人1ラウンド1回、同じ送信IDの再送は重複適用しません。過去10ラウンドの結果・送信IDだけを保持します。
- イベント終了後は参加・戦闘操作を停止します。既存のイベント削除CLIで保存期限後のゲストを削除すると、戦闘状態も削除します。リセットでも部屋の参加者情報・結果を消します。

## 既存サーバーへの反映

反映するブランチは `codex/production-raid`。DB移行は `202610260001_production_raid` のテーブル追加だけです。既存の本番用Compose設定を保持します。管理者アカウントはDBに残りますが、発行時のパスワードJSONはコンテナー内のファイルなので、更新前にパスワードを手元へ保存してください。

SSHで接続したUbuntu上で、1行ずつ実行します。途中で失敗したら次へ進まず、結果を確認します。

```bash
cd /home/ubuntu/4pro_WEBGAME
git status --short
sudo docker compose ps
sudo docker compose exec -T web node -e 'console.log(JSON.stringify({APP_URL:process.env.APP_URL,EVENT_ID:process.env.EVENT_ID,ENABLE_DEV_SIMULATOR:process.env.ENABLE_DEV_SIMULATOR},null,2))'
```

`APP_URL` が公開HTTPS URL、開発シミュレーターが `false` であることを確認します。未追跡の `compose.override.yaml` は保持します。ソースのローカル変更がある場合は、内容を確認してから進めます。

更新前のDBと設定を保存します。

```bash
raid_backup="$HOME/fourpro-backups/fourpro-before-raid-$(date +%Y%m%d-%H%M%S)"
(
umask 077
mkdir -p "$HOME/fourpro-backups"
sudo docker compose exec -T db pg_dump -U fourpro -d fourpro -Fc > "$raid_backup.dump"

```

作業ツリーが反映可能な状態になってから取得・ビルドします。`--ff-only` が失敗した場合は停止し、ブランチの差分を確認してください。

```bash
git fetch origin
git merge --ff-only origin/codex/production-raid
sudo docker compose build web
sudo docker compose up -d --no-deps web
sudo docker compose logs --tail=80 web
curl --retry 10 --retry-connrefused --retry-delay 2 --max-time 10 -fsS http://127.0.0.1:3000/api/health
```

コンテナー起動時に `db:migrate`→`db:seed`→本番起動が実行されます。通常の更新でDBボリュームの削除やDBリセットは行いません。`/api/health` の正常応答に加え、実機で管理者ログイン・参加QR・スマホ2台以上の入力・HP更新・スクリーン再読み込み・リセット・既存のNFC URLからの獲得を確認します。

バックアップの `umask 077` は括弧内のサブシェルだけに適用します。シェル全体へ設定したままGitでファイルを取得すると、ソースが所有者しか読めない権限になる場合があります。Dockerfileではコピー時に `node` へ所有権を設定し、ホスト側で制限されたソースも非rootユーザーで読み込めるようにしています。

旧Dockerfileで `EACCES: permission denied, open '/app/prisma/schema.prisma'` が出て再起動を繰り返す場合は、`umask 022` を実行してから、この修正を取得しwebを再ビルド・再作成します。既に作られたファイルの権限は `umask` だけでは変更されません。DBコンテナーやDBボリュームを削除する必要はありません。

更新後に問題がある場合はログを保存し、控えたコミットへソースを戻してwebを再ビルドする方法を検討します。追加テーブルは旧版の既存テーブルと独立しているので、アプリを戻すためだけに本番DB全体を復元する必要はありません。

## 待機中の参加者整理と参加締切

- 操作バーの「参加者管理」から、閉じた端末・誤って入った人を「参加解除」できる。参加者数とボスHP・全体攻撃を待機中だけ再計算する。解除された人はその部屋では再参加できず、リセット後に新しいQRから参加できる。所持・収集・討伐記録は削除しない。
- スマホの「参加取消」で待機中の本人が退出できる。再参加する場合も本人が参加ボタンを押す。ブラウザを閉じたことだけを根拠とする自動退出は行わず、閉じた人の整理は運営が行う。
- 開始後はQRと拡大QRダイアログを非表示にする。新規参加・参加解除・退出はサーバーも拒否する。参加済みの人の再接続は可能。
- 本番の参加URLは `/battle/raid?room=部屋ID`。旧QRや部屋IDなしのURLは新しい参加に使わない。リセットで展示キャラ獲得用 `/acquire/...` のQRは変更しない。
- `GET /api/raid/entry?roomId=...` は管理者のみが、現在の待機中の部屋のQRを取得できる。`POST /api/raid` の参加には現在の部屋ID、解除には管理者認証と参加者ID、退出には本人のゲスト認証が必要。DBスキーマの移行は不要。ローカル開発専用モードは従来の確認導線を残す。

## スクリーンのBGM

- 画面下の「BGM オフ」を押すと再生し、「BGM オン」を押すと消音する。ページを開き直すとオフに戻る。次戦の準備や同期リセットではオン・オフ設定を保つ。スマホの参加画面では再生しない。
- 待機中は `LobbyBGM` を繰り返す。スクリーン下の「バトルBGM」で `BattleBGM1`・`BattleBGM2`・`BattleBGM3` から選ぶ（初期値は1）。開始時に選択した曲を先頭から再生し、0.65秒でクロスフェードする。バトルが長引いても同じ曲を繰り返す。結果画面もその曲を続け、次戦の待機に戻るとロビー曲を先頭から再生する。ラウンド進行や同期の更新では再スタートしない。
- 選択は次戦の準備や同期リセットを通じて維持し、ページ再読込で1に戻る。戦闘中に曲を選び直すと、その曲を先頭から再生する。演出確認ページにも同じ選択欄・BGMボタンを用意し、待機演出ではロビー曲、それ以外では選択したバトル曲を使う。
- 提供音源は `music/LobbyBGM.mp3` と `music/BattleBGM1.mp3`・`BattleBGM2.mp3`・`BattleBGM3.mp3`。元ファイルを保ち、同じ内容を `public/music/` に配置する。本番反映にはこの4ファイルも含める。DB移行は不要。以前のWAVは再生対象から外す。
- オンにしたときに必要な曲を取得・デコードし、ロビー中は選択したバトル曲も先読みする。選んでいない曲は取得しない。デコード結果を画面内で共有し、ループのたびに取得・デコード・音源の作り直しは行わない。曲が変わると前の音源をフェード後に停止・解放し、オフではマスター音量を下げてAudioContextを休止する。離脱時は音源とコンテキストを解放する。読み込み中のオフ操作・選択変更・取得失敗後の再試行にも対応し、古い選択の読み込みが遅れて終わっても再生しない。
- 操作者のクリックから音声を開始するのは、[ブラウザの自動再生制限](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices#autoplay_policy)に対応するため。音源の繰り返しには [AudioBufferSourceNode.loop](https://developer.mozilla.org/en-US/docs/Web/API/AudioBufferSourceNode/loop) を使う。

## 攻撃・反撃の効果音

- スクリーンと演出確認ページに「効果音 オフ／オン」を追加した。初期状態はオフで、押して有効にする。BGMと独立して切り替えられ、次戦の準備では設定を保持し、ページを開き直すとオフに戻る。スマホからは再生しない。演出確認ページでも音声・表示の操作バーを演出選択と分け、ボタンが重ならないようにしている。
- 通常攻撃は短く鋭い、金属の胴鳴りを伴う打撃音。2倍攻撃は低い爆発音に、崩れるようなノイズと長めの残響を重ね、音色から聞き分けられるようにした。低音を出しにくいスピーカーでも厚みが伝わるよう倍音も重ねる。全キャラ共通の音をWeb Audioで合成するため、追加音源の取得はない。効果音の長さは通常0.42秒・2倍攻撃0.9秒。BGMと合わせても過大な音量にならないよう出力を抑えている。
- ボスの反撃には、2倍攻撃の爆発音を土台に低い咆哮・ブレス・長めの残響を重ねた専用音を追加した（1.3秒）。2倍攻撃そのものの音は維持する。同じ「効果音」ボタンで切り替え、反撃の命中（演出開始から1550ms）に合わせて全体で1回だけ鳴らす。
- 攻撃演出の命中（ヒットストップ開始、通常は演出開始から650ms）に同期する。複数人の攻撃は1回の共通音にまとめ、キャラ数で音を重ねない。同期の更新や同じ演出中の再描画でも重複再生しない。
- 命中前に演出を変えた場合や、一時停止中には鳴らない。オフのまま命中した後でオンにしても、過去の音は鳴らさない。「今の演出をもう一度」で再生したときは新しい命中に合わせて鳴る。消音・演出変更・タブ非表示・離脱時は残っている打撃音を止める。
