# 同期レイドの攻撃・回復モーション

`3Dmodels/モーション統合/` を再出力の原本管理フォルダとし、骨・パーツ・マテリアルを含む独立したGLBを `public/models/motions/` に生成する。「モーションファイル」「モーションファイル2」「モーションファイル3」の48ファイルをSHA-256で照合し、完全重複16件をまとめた32種類を保管する。アップロード元は削除・変更しない。Blenderのオブジェクト名や骨が違うファイルへキーだけを流用せず、モーション用GLBのモデルを行動中だけ表示し、終了後はDBの通常モデルへ戻す。

統合先の `inventory.json` に元の場所・ハッシュ・採用状態を記録する。キャラID別フォルダの攻撃／回復が採用対象、`references/` が別形式の書き出し・行動区別なしGLB・未使用のボス演出。既存の確認済みBlender原本と同じファイルが含まれていた場合はそれを採用し、追加GLBは参照用に保管する。元の素材が不足している2行動は原本を保持し、実行用として登録しない。

## 再出力

### 2026-10-31の回復テスト素材

ユーザーの指定により、Mモンとリセンコの回復を「モーションファイル3」のテストGLBへ差し替える。`forest-golem/heal-test.glb` と `flame-dragon/heal-test.glb` が採用原本。以前の各 `heal.glb` は統合フォルダに保持し、inventoryでは参照用にする。配信用は従来と同じ `m-heal.glb`／`s-heal.glb` なので、スマホ・スクリーン・モデル確認の共通設定に反映する。

- Mモンは約5.93秒。本体と球の動きがあるが、開始時の大きな球が本体を隠す点を保持する。遠くの制作参照平面2枚だけを除き、本体のキー・球のサイズは変えない。
- リセンコは約3.47秒。表示されない「ビーム先端」の移動だけがあり、本体・ビームは静止する。これは修正済みモーションではなく、既知の状態のまま指定された素材を採用するもの。Blenderでの本体名 `body` を画角基準とする。新GLBは既に正面が+Zなので、回復だけ `actionYaw.heal=0` を焼き込み、DBの通常モデルの角度−90度は保持する。
- 既存の攻撃GLB、通常モデル、図鑑画像、回復量、2.2秒の行動枠、DBは変更しない。確認後のコミット・mainへの統合・本番反映は別途行う。

この2行動だけを書き出す場合、下記Blenderコマンド末尾に `-- --id=forest-golem,flame-dragon --action=heal` を付ける。

検証は本番形式のビルド、単体テスト186件、関連ブラウザテスト3件が成功。Mモン・リセンコの攻撃／回復／停止後の通常モデルへの復帰、レイド演出デモのキャラ切り替えと回復、本番APIへ行動を送信しないことを確認した。最後の向き調整後もGLB・原本管理の関連単体テストを実行した。リセンコの静止ビームとMモンの大きな球は原本由来の既知の見た目であり、動くように修正したという意味ではない。

```powershell
node scripts/merge-raid-motion-sources.mjs
& 'C:\Program Files\Blender Foundation\Blender 5.2\blender.exe' --background --factory-startup --disable-autoexec --python-exit-code 1 --python scripts/export-raid-motions.py
node scripts/build-raid-motion-manifest.mjs
```

取り込みコマンドは元の2フォルダを読み、異なる内容で統合先を自動上書きしない。統合済みの原本から再出力するだけなら、取り込みを繰り返す必要はない。採用元・向き・処理条件は `scripts/raid-motion-sources.json` で管理する。

1体だけならBlenderコマンドに `-- --id=temp-09` 等を付ける。複数体は `-- --id=forest-golem,flame-dragon,temp-07,temp-10` と指定できる。拡張子が `.blend 回復` 等だったファイルは内容を変えず統合先で `.blend` 名に統一した。glTFの+Yが上・+Zが正面になるよう、出力GLB内の共通親に座標変換を保持する。デンラコは旧原本の上下を反転し、ブシラッコはモーション原本ですでに上下が直っているため二重反転しない。DBの通常モデルの正面角度は変更しない。

M科の攻撃GLBは回復・通常モデルと元の正面方向が異なるため、`actionYaw` で攻撃だけの向きを指定してGLB内に焼き込む。ブラウザでの回転による補正やDBの通常モデルの角度変更は行わない。

書き出し範囲は250フレーム等のシーン設定ではなく、実際のアクションのキー範囲から決定する。Morinokamiの高密度部分は骨を残して軽量化する。ボスはArmatureを残し、Mirror等を先に評価して左右の欠けを防ぐ。通常キャラの元モデルや図鑑画像は変更しない。

追加素材の高密度メッシュは、配信用のコピーだけを軽量化する。トショカンのように面ごとの重複頂点が単純な削減を妨げる場合は、近接頂点を統合してから削減する。Mモンの大きいテクスチャは最大1024pxに縮小する。制作中の離れた参照平面と、表示対象を持たない補助オブジェクトは `excludeObjects` の指定に従って配信用から除く。

`bodyPrefixes` に指定した本体にはGLB内の `raidMotionBody` メタデータを付ける。飛び道具や大きな回復エフェクトを残しつつ、本体を基準に正規化と固定画角を計算する。本体が下降するモーションは最下点が床上になるよう全体を配置し、原本のキーやパーツ間の動きは変更しない。従来のGLBはこのメタデータがないため、既存の表示範囲の計算を維持する。

E科のアップロードGLBには、通常の `.blend` で非表示の制作素材（別置きのヘッドホン・リュック・平面等）も含まれている。`visibilitySource` の元Blender原本を読み、非表示オブジェクトをモーションの書き出しから除外する。原本にない新しい攻撃／回復エフェクトは残す。胴体の拡大縮小キー（攻撃で最大約1.57倍、回復で最小約0.8倍）は原本由来であり、キー自体は変更しない。

## 再生と同期

- 会場スクリーンは既存の共通演出時計の `visualMs` を使う。ヒットストップ・一時停止・タブ非表示による停止もその時計に従う。攻撃と回復が混在しても参加者IDごとに選んだモーションを同時再生する。
- スマホは本番サーバーが通知した `actionTurn` の増加に一度だけ反応する。送信ボタンを押した段階では再生しない。未送信者と、途中から開いた画面の過去の行動は再生しない。再読み込み・定期取得で繰り返さない。
- パーツごとに分かれたGLB内の複数クリップをまとめ、空白の開始時間を除いて再生する。元のキー間の時間比は維持し、通常キャラは2.2秒の行動枠に収める。ループせず、行動枠の後は通常モデルに戻す。
- 同じキャラの参加者も別のMixer・骨・表示状態を持つ。メッシュ／マテリアル／クリップのみ同じライブラリで共有する。モデル差し替え・離脱・画面終了ではMixerのバインドを解除する。
- スマホの表示範囲は通常モデル・攻撃・回復の本体の移動範囲を含めて一度決め、待機／再生／停止で画角を切り替えない。移動中の見切れと、開始・終了時に急に縮む／戻る見え方を防ぐ。範囲を共有テンプレートの読み込み時に計算し、毎フレームのCPUスキニング計算を避ける。飛んでいく弾や画面外まで広がるエフェクトのために本体を縮小しない。動きを減らす設定ではモーションを再生しない。素材未読込・読込失敗では通常モデルと既存エフェクトを保つ。

HP・ダメージ・回復量・受付秒数・結果の保存処理は変更しない。モーションの終了や失敗が、サーバー側の行動結果を左右することはない。

## 既存DBとサーバー反映

モーション対応そのものはスキーマやDB内容を変更しない。`bundled-character-motions.json` に記録した通常GLBのSHA-256と正面角度がDBの登録モデルと一致する場合にだけ、`/api/character-models` へモーションURLを付ける。管理画面で独自モデルや角度へ変更した場合は自動で無効になり、別モデルへの誤適用を防ぐ。モデルIDごとのハッシュはサーバー内で最大128件キャッシュし、15秒ごとの取得でGLB本体を何度も読まない。

配布にはコード・マニフェスト・`public/models/motions/` を同じコミットから反映する。既存のデンラコ／ブシラッコは、先行する[通常モデルの向き修正](3d-models.md)もDBに反映済みである必要がある。モーションのためにキャラを作り直したり、NFC・所持データを変更したりする必要はない。

## 確認

`/models` の対応キャラに「攻撃」「回復」「停止」が出る。`/models?character=temp-09` などで1体だけ確認できる。静止した図鑑画像と通常GLBのダウンロードは従来どおり。レイド会場の演出デモではボスの反撃から攻撃モーションを確認できる。

`/raid/screen?demo=effects` の「確認するキャラ」で、DBに登録されたキャラを選ぶと、その1体を会場と同じ向き・演出で確認できる。読み込み後に「通常攻撃」「2倍攻撃」「自己回復」を押し、「今の演出をもう一度」で繰り返せる。`&character=temp-09` 等で確認対象を最初から指定できる。「4人デモ」は元の固定チームへ戻る。モーションのないキャラは標準演出になる。この選択は画面内だけの確認用データで、本番レイドへの参加・行動送信・DB変更は行わない。

単体テストは実GLBの構造・キー、複数クリップの結合、参加者間の独立性、通常モデルへの復帰とモデル照合、統合原本のハッシュ・重複管理、本体基準の画角と床位置を確認する。ブラウザーテストは10体の有効な攻撃／回復・停止・従来演出の維持と、同一キャラ2人が本番APIを通じて攻撃／回復を選び分ける同期ラウンドを検証する。追加キャラでは単に再生状態を見るだけでなく、実画像で本体が小さく消えていないことも確認する。

2026-10-28に本番用ビルドと型チェック、関連単体テスト21件、ブラウザー11件が成功した。複数WebGL画面の録画は受付中の描画を遅らせるため、同期モーションの検証では受付中の行動を本番APIで送信し、画面ごとの再生を確認する。操作ボタン経由のラウンド・再接続は別の既存ケースで確認した。スマホ実機での確認は別途行う。本番サーバー／本番DBには未反映。

同日のE科の追加調査では、元GLBと再出力GLBの本体各部を同時刻で比較し、動くパーツの座標と時間範囲が一致することを確認した。非表示素材の除外と画角固定を修正し、混入防止／画角の追加単体テストとE科の攻撃・回復・停止後の表示を確認する。

2026-10-29の追加素材統合では、本番ビルド・型チェック・単体テスト171件・モーションのブラウザテスト13件が成功した。追加4体の有効な6行動、既存6体、ボス、停止後の復帰、演出デモの選択を確認した。画像確認で見つかった参照平面による縮小・床下への沈み・M科攻撃の正面方向を修正し、M科は最終書き出し後にも表示を再確認した。モデル・NFC・所持・戦績などの本番DBデータは変更していない。本番サーバーには未反映。
